CS 499 / Milestone Two

Artifact Description

The artifact I selected for the Software Design and Engineering category is my Travlr Getaways full-stack web application, originally developed for CS 465: Full Stack Development I. The application was created as a MEAN stack project using MongoDB, Express, Angular, and Node.js. It consists of a customer-facing travel website, an Angular administrative single-page application, and an Express API connected to MongoDB. The administrative portion allows trip information to be created, viewed, updated, and managed through the web application.

I selected Travlr because it demonstrates several areas of software engineering within one artifact. It includes frontend development, backend API development, database integration, authentication, routing, and communication between multiple application layers. At the same time, my original implementation contained several areas that could be improved based on the knowledge and experience I have gained since completing CS 465.

Justification for Inclusion and Enhancement

The original Travlr application demonstrated my ability to construct a functioning full-stack application, but my code review identified several weaknesses in its authentication, API design, security, and TypeScript implementation.

One of the most significant issues was the authentication system. The original login controller contained a hard-coded administrator email and password. It also signed JSON Web Tokens using a secret value written directly into the source code. Although the application contained a MongoDB User model and the Angular application sent JWTs with administrative API requests, the backend did not actually verify those tokens before allowing trip records to be created, updated, or deleted.

I substantially redesigned this portion of the application. Authentication now uses the MongoDB User model rather than comparing credentials against hard-coded values. User passwords are stored using bcrypt password hashing with a work factor of 12. During login, the application retrieves the user from MongoDB and compares the submitted password against the stored hash. Email addresses are also normalized before lookup. Authentication failures return the same generic response for an unknown user or incorrect password, reducing the amount of account information exposed by the API.

I also moved the JWT signing secret from the source code into an environment variable loaded through dotenv. The application checks that the secret is configured before issuing a token. Successful authentication produces a JWT containing the user's identifier and email address with a one-hour expiration.

Another important enhancement was adding JWT authentication middleware to the Express API. The middleware extracts the Bearer token from the authorization header and verifies its signature and expiration. Trip information remains publicly readable, but creating, updating, and deleting trips now requires authentication. This preserves the public functionality of the travel application while restricting administrative operations.

I also improved the trip controllers. The original implementation passed req.body directly to Trip.create() and used Object.assign() when updating an existing document. These approaches allowed the request body to control which properties were assigned to a database object. The enhanced implementation defines an explicit whitelist of permitted trip fields and constructs the database object from those fields. Required fields and the trip start date are validated before database operations occur. Error handling was also changed so internal errors are logged on the server while clients receive controlled responses and appropriate HTTP status codes.

Finally, I improved the Angular application's type safety. The original services relied heavily on the TypeScript any type. I created interfaces for login credentials, authentication responses, and Trip objects. HTTP operations now specify the type of information expected by both the frontend and API. This provides a clearer contract between application layers and allows TypeScript to detect incorrect properties during development rather than allowing those problems to appear at runtime.

Course Outcomes

This enhancement primarily demonstrates progress toward Course Outcomes Three, Four, and Five.

Course Outcome Three focuses on designing and evaluating computing solutions using computer science practices while considering tradeoffs. During the enhancement, I evaluated the original application's architecture rather than simply adding new functionality. For example, I chose to keep GET requests for trip information public while requiring authentication for POST, PUT, and DELETE operations. This preserves the application's customer-facing functionality while restricting operations that modify database information. I also replaced broad object assignment with explicit field whitelisting and validation to create a more predictable API contract.

Course Outcome Four is demonstrated through the implementation of several technologies and techniques that improve the value and reliability of the application. MongoDB is now integrated into the authentication process, bcrypt provides secure password hashing, JWT middleware provides stateless API authorization, environment variables separate configuration from application source code, and TypeScript interfaces improve communication between the frontend and backend. These technologies work together as part of the application's overall architecture rather than as isolated additions.

Course Outcome Five is the outcome most directly demonstrated by this enhancement. My code review identified several security weaknesses that were not obvious simply from using the original application. For example, the Angular application already sent JWTs with administrative requests, which could create the appearance that the endpoints were protected. Testing the API directly showed that an unauthenticated client could still create, update, or delete trips because the server never verified the token. The enhanced application now verifies JWTs before permitting those operations. Hard-coded credentials and signing secrets were also removed, passwords are hashed rather than stored or compared as plaintext, authentication responses disclose less information, and request data is restricted before reaching database operations.

My planned course outcomes did not require major changes during implementation. Outcomes Three, Four, and Five remained the strongest matches for the artifact. The completed enhancement provided more evidence for Outcome Five than I initially expected because testing revealed that authentication existed on the client side without corresponding authorization enforcement on the server.

Reflection on the Enhancement Process

Enhancing Travlr showed me the difference between making an application function and engineering an application to behave predictably and securely. The original project worked from a user's perspective, but reviewing the implementation exposed design decisions that I would not make the same way today.

One challenge occurred while implementing bcrypt password hashing. My initial Mongoose pre-save middleware used a next callback pattern that did not work correctly with the version of Mongoose installed in the project. The application produced a TypeError indicating that next was not a function. I investigated the failure and changed the middleware to use the current asynchronous middleware behavior. After making the change, I verified directly through MongoDB that the administrator password was stored as a bcrypt hash rather than plaintext.

Testing was an important part of the enhancement. I tested missing login information, incorrect passwords, nonexistent users, missing trip fields, invalid dates, field whitelisting, successful CRUD operations, nonexistent records, requests without JWTs, invalid JWTs, and requests containing valid JWTs. I also built the Angular application after introducing the TypeScript interfaces to ensure that the stronger typing did not introduce compilation errors.

Another troubleshooting situation occurred while testing authentication through Angular. The interface initially displayed an "Invalid username or password" message even though the credentials had already been verified through direct API testing. Inspecting the browser's HTTP error showed a status of zero rather than an authentication failure. This eventually revealed that the Express backend was not running alongside the Angular development server. This reinforced the importance of examining the actual error information instead of assuming that a user-facing message accurately identifies the underlying problem.

The final end-to-end test created a trip through the Angular administrative interface. The request traveled through the typed Angular service, included the stored JWT, passed the Express authentication middleware and trip validation, was stored in MongoDB, and was returned to the Angular interface for display. The test record was then removed using an authenticated request.

Overall, this enhancement demonstrates how my approach to software development has progressed since the original artifact was created. My focus is no longer limited to whether an application produces the expected output. I now consider how data enters the system, which users should be permitted to perform an operation, how credentials and configuration information are protected, how application layers communicate, how failures are handled, and how the implementation can be tested to verify that its security controls actually work.
