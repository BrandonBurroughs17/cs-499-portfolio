CS 499 / Milestone Four

Artifact Description

For my database enhancement, I selected my Grazioso Salvare Rescue Animal Dashboard that I originally created in CS 340: Client/Server Development. The project uses Python, MongoDB, Pandas, Plotly Dash, and Dash Leaflet to provide an interactive dashboard for viewing animal shelter data. The application connects to a MongoDB database through a Python CRUD module and allows users to filter animals based on different rescue categories, including Water Rescue, Mountain/Wilderness Rescue, and Disaster/Tracking. The dashboard also displays the results in a data table, creates a visualization of the most common breeds, and displays the selected animal's location on an interactive map.

I selected this artifact because it gave me an opportunity to improve both the database layer and the way the application interacts with its data. Although the original project successfully demonstrated CRUD operations and MongoDB integration, reviewing it later showed several areas that could be improved. The original implementation had limited input validation, duplicated database code, hard-coded database credentials, broad exception handling, and no explicit connection validation or index management. Parts of the dashboard also relied on numeric DataFrame column positions, which made the application dependent on the exact order of fields returned from the database. These issues made the project a good candidate for demonstrating how my database development skills have improved since I originally completed CS 340.

Justification for Inclusion

I included this artifact in my ePortfolio because it demonstrates my ability to work with databases as more than just a place to store and retrieve information. The original project showed that I could connect a Python application to MongoDB and perform CRUD operations, but my enhancements focused on making that database layer more secure, reliable, maintainable, and practical for a real application.

One of the largest improvements I made was redesigning the AnimalShelter class. The original version accepted a username and password but did not actually use those values when creating the MongoDB connection. Another version of the CRUD module contained the username and password directly in the source code. I removed these hard-coded credentials and changed the application to use environment variables for its MongoDB configuration. This keeps sensitive information separate from the source code and allows the same application to be configured for different environments without modifying the program itself.

I also improved the reliability and security of the CRUD operations. The enhanced class validates data and queries before sending them to MongoDB and uses PyMongoError rather than catching every possible exception. Update and delete operations now reject empty queries, which reduces the possibility of accidentally modifying or deleting an entire collection. Updates are also checked for MongoDB update operators before they are executed. I added a connection timeout and an explicit MongoDB ping so that connection problems are identified when the database object is created instead of failing later during an operation.

Another improvement was database index management. I added functionality for creating and inspecting an index based on fields used repeatedly by the rescue filters. This allowed me to consider the tradeoff between query performance and the additional storage and write overhead associated with indexes. I also learned that an index does not automatically make every query faster. The rescue filters use regular expressions for breed matching, which can limit how effectively a standard MongoDB index can be used. This was important because it required me to evaluate how the application actually queries its data instead of simply adding an index and assuming performance had improved.

I also improved the surrounding application code. The two separate CRUD implementations were consolidated so that AnimalShelter.py serves as the maintained database implementation while CRUD_Python_Module.py provides compatibility with the original project. I updated the dashboard from the older JupyterDash implementation to the current Dash implementation because the original code was no longer compatible with the current library. I also replaced hard-coded DataFrame column positions in the map callback with named fields such as location_lat, location_long, breed, and name. This makes the application less dependent on column ordering and easier to maintain when the database structure changes.

Finally, I added scripts for importing and cleaning the dataset as well as testing CRUD operations, validation rules, and rescue queries. Using the 10,000-record animal shelter dataset, I verified that the database contained 519 Water Rescue matches, 197 Mountain/Wilderness Rescue matches, and 22 Disaster/Tracking matches. I then confirmed that those same filters correctly updated the dashboard's table, breed visualization, and interactive map. These enhancements demonstrate stronger database development practices as well as my growth in testing, security, application integration, and maintainable software design.

Course Outcomes

The enhancements to this artifact primarily support Course Outcomes Three, Four, and Five. I believe the work completed during this milestone met the outcomes I originally planned for the artifact, while also demonstrating more growth in secure development than I initially expected.

Course Outcome Three focuses on designing and evaluating computing solutions while considering tradeoffs. This outcome is demonstrated through my evaluation of MongoDB indexing and the existing rescue queries. Instead of assuming that adding an index would automatically improve performance, I considered how the age range and regular-expression breed filters interact with MongoDB indexing. I also considered the additional storage and write overhead that comes with maintaining indexes. The changes to the map callback demonstrate a similar design decision because replacing numeric column positions with named fields trades a small amount of additional code for significantly better readability and maintainability.

Course Outcome Four is the strongest outcome demonstrated by this enhancement. I used MongoDB, PyMongo, Pandas, Dash, and Dash Leaflet together to create a complete database-backed application. I improved the CRUD layer, added connection validation and configuration management, consolidated duplicate code, modernized the dashboard framework, and created supporting scripts for importing, cleaning, and testing the data. I also tested the enhanced application against 10,000 database records and verified that the database queries produced the expected results throughout the dashboard. These changes demonstrate my ability to use appropriate techniques and tools to develop a solution that provides value while remaining maintainable and testable.

Course Outcome Five is also strongly represented because I approached the database enhancement with a security mindset. I removed database credentials from the source code, moved configuration to environment variables, added validation to database operations, and prevented update and delete operations from accepting empty queries. These safeguards reduce the possibility of credential exposure and unintended bulk changes to the database. I also replaced broad exception handling with database-specific error handling so that failures are handled more intentionally.

I did not need to significantly change the course outcomes I originally selected for this artifact. However, the enhancement process showed that Outcome Five applied more strongly than I initially anticipated. What began primarily as a database and maintainability enhancement also became an opportunity to address several security weaknesses in the original implementation.

Reflection on the Enhancement Process

Working through this enhancement showed me how much differently I approach database development now compared to when I originally completed the project in CS 340. The original application worked for the requirements of the course, but revisiting it made several weaknesses much more obvious. I was no longer looking only at whether the application could connect to MongoDB and display data. I was also considering security, maintainability, error handling, data integrity, testing, and how changes in one part of the application could affect another.

One of the biggest challenges was recreating the original development environment. The project was originally developed in a course-provided environment, so running it locally required configuring a Python virtual environment, installing the necessary dependencies, running MongoDB locally, and restoring the animal shelter dataset. Once the 10,000 records were imported, I was able to test the database independently before testing the complete dashboard. This helped me separate database problems from application problems instead of trying to troubleshoot the entire system at once.

Testing also exposed issues that I would not have noticed by only reviewing the source code. For example, the original dashboard used JupyterDash, which was no longer compatible with the current version of Dash. I updated the application to use the current Dash implementation and verified that the dashboard could run again. Cleaning an unnecessary CSV-generated field also changed the DataFrame's column positions, which demonstrated why the original map implementation was fragile. Replacing numeric positions with named fields allowed the map to continue working regardless of the order of the columns.

I also learned more about designing safeguards around database operations. An empty query can have a much larger impact on an update or delete operation than it does on a read operation. Because of this, the enhanced CRUD layer allows an empty query when reading all records but rejects empty queries for updates and deletes. Testing these cases helped me better understand how validation should depend on the purpose and potential impact of an operation rather than applying the same rule everywhere.

Overall, this enhancement gave me a better understanding of what separates functional code from maintainable and secure software. The final application still performs the same core job as the original project, but the underlying database layer is more reliable, configurable, testable, and secure. The process also reinforced the importance of testing changes against real data and evaluating the effects of design decisions instead of assuming that a change is an improvement simply because the code runs.
