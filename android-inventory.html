Artifact Description

The artifact I selected for my Algorithms and Data Structures enhancement is the Android Inventory application that I originally created for CS 360: Mobile Architecture and Programming. The application was developed in Java using Android Studio and uses SQLite for persistent data storage. The original application allowed a user to log in, add inventory items with a name and quantity, display the inventory using a RecyclerView, and request permission to send SMS inventory alerts.

The original version successfully demonstrated the basic functionality of a mobile inventory application, but its inventory management capabilities were limited. When the inventory screen loaded, the application retrieved every item from the SQLite database and stored the results in an ArrayList<Item>. The user had no way to search, sort, or filter the inventory. This became the focus of my enhancement because it provided an opportunity to improve the usability of the application while demonstrating my understanding of algorithms, data structures, database queries, and computational tradeoffs.

Justification for Inclusion

I selected this artifact for my ePortfolio because the enhancement demonstrates how algorithms and data structures can be applied to improve an existing application rather than simply adding more features. I added inventory searching, four sorting options, and low-stock filtering while maintaining the existing SQLite database and RecyclerView structure.

For searching, I added a parameterized SQLite query that uses LIKE to retrieve inventory items matching the text entered by the user. The search is performed as the user types. Instead of retrieving the entire inventory and then searching every item in Java, the database is responsible for identifying the matching records before those records are converted into Item objects. This reduces the amount of unnecessary data passed from the database layer to the application when the search produces a smaller result set. The use of %searchText% may still require SQLite to examine the available rows, so this does not necessarily change the worst-case search complexity to something better than O(n). However, it improves the separation of responsibilities and avoids creating Java objects for database rows that do not match the search.

I also implemented sorting using the application's existing ArrayList<Item> and Java's Collections.sort() with different comparators. The user can sort the inventory alphabetically from A to Z or Z to A, as well as by quantity from low to high or high to low. Comparison-based sorting provides approximately O(n log n) performance for the collection being displayed. I intentionally performed this operation in memory because the inventory items have already been loaded for display, so changing the sort order does not require another database query.

The low-stock feature demonstrates a linear filtering algorithm. I created separate collections for the items returned by the database and the items currently displayed in the RecyclerView. When the low-stock option is enabled, the application traverses the source collection once and adds items with a quantity of five or fewer to the displayed collection. This operation has O(n) time complexity because each item is examined once. Maintaining separate ArrayList objects also prevents the filter from destructively removing items from the original result set.

These changes demonstrate why the ArrayList remains an appropriate data structure for this application. The RecyclerView displays an ordered collection of items, and an ArrayList provides efficient indexed access, straightforward iteration, and compatibility with Java's collection sorting utilities. The enhancement also allowed search, filtering, and sorting to work together. SQLite first retrieves the appropriate records, the application filters the resulting collection when necessary, and the final collection is sorted before being displayed.

Course Outcomes

This enhancement primarily supports Course Outcome Three, which focuses on designing and evaluating computing solutions using algorithmic principles and computer science practices while managing tradeoffs. The enhancement required me to consider whether operations should be performed by SQLite or by the Java application. I chose database-side searching while using in-memory filtering and sorting for data that had already been retrieved. This allowed me to evaluate the advantages and limitations of each approach instead of using the same solution for every operation.

The enhancement also supports Course Outcome Four because I used appropriate tools and techniques to improve the value of the application. The new functionality makes the inventory system more useful as the number of stored items increases because users can locate items, identify low-stock inventory, and reorganize the displayed data without manually searching through the entire list.

After completing the enhancement, I do not believe the course outcomes identified in my original plan need to be changed. Outcomes Three and Four remain the strongest matches for this artifact. Although I also corrected some existing application behavior and improved input validation during development, I do not consider those changes sufficient to claim that this artifact primarily demonstrates the security-focused course outcome.

Reflection on the Enhancement Process

Enhancing this artifact showed me that improving existing software involves more than adding new functionality. Before beginning the algorithms and data structures work, I had to get the older Android project running correctly in the current development environment. I initially opened the parent project directory rather than the actual Gradle project, which prevented Android Studio from recognizing the application as a runnable Android module. After correcting the project path and JDK configuration, I was able to establish a working baseline before making changes.

Testing the original application also revealed problems with its login behavior. The login button could create an account when one did not already exist, while the intended Create Account button was not connected to the application logic. I corrected this behavior before continuing with the planned enhancement so that I could test the inventory features from a reliable baseline. I also improved inventory input validation so blank values, negative quantities, and invalid numeric input are handled more appropriately.

The most valuable part of the enhancement was deciding where each operation should occur. It would have been possible to perform searching, filtering, and sorting entirely in Java or entirely through SQLite queries. Instead, I used different approaches based on the operation being performed. Search is handled through a targeted SQLite query, low-stock detection uses an O(n) traversal of the Java collection, and sorting uses Java comparators and Collections.sort(). This gave me a better understanding of how data structures, algorithms, database operations, and user interface components interact within a complete application.

The completed enhancement is significantly more functional than the original artifact while preserving its original purpose. More importantly, the process allowed me to demonstrate that I can analyze an existing solution, identify its limitations, evaluate multiple implementation approaches, and make design decisions based on algorithmic efficiency and maintainability.
